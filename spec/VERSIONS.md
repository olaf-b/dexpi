## Why these are vendored rather than fetched

Every DEXPI XML file imports its models by URI:

    <Import prefix="Core" source="https://data.dexpi.org/models/2.0.0/Core.xml"/>

Those URIs do **not** resolve. As of 2026-09-10 `data.dexpi.org` serves a certificate
for `my.exacon.cloud` (so TLS verification fails) and returns 404 regardless. Treat
model URIs purely as namespace identifiers; never dereference them at runtime.

## Known gaps and quirks

- **`MetaData` is imported but not shipped.** The generated models contain
  `<Import prefix="MetaData" source=".../MetaData.xml"/>` and reference
  `MetaData/description`, but no `MetaData.xml` is produced by the build or present
  upstream. A reader must tolerate unresolved imports.
- **`Builtin` is implicit.** `Builtin/String`, `Builtin/Double`, `Builtin/Undefined`
  and friends are referenced without a corresponding `<Import>` element.
  `models/Builtin.xml` is generated separately and must be loaded unconditionally.
  Note its URI sits under `meta/1.0.0/`, not `models/2.0.0/`.
- **The schema is a release candidate** (`DEXPI_XML_Schema_RC_1.xsd` upstream).
  Expect churn.
- **`Composition.MoleFractiona` is misspelled in the standard.** Its siblings are
  `MassFractions`, `MassFlow` and `MoleFlow`, so the intended name is plainly
  `MoleFractions`. The typo is in DEXPI 2.0.0 as released, so a conformant document must
  use the misspelling. Worth reporting upstream.
- **`Core/Diagram.NodePosition` has no concrete subtype usable by a process diagram.**
  The only two, `PipingNodePosition` and `InstrumentationNodePosition`, live in the Plant
  model. A BFD therefore cannot record node positions in `NodePositions`; position is
  carried implicitly in the coordinates of the graphical primitives. Moving a box means
  rewriting a polygon's points, not updating an x/y field.
- **A process graph must be closed.** `Port.ConnectorReference` and `Stream.Source`/
  `Target` are all `lower="1"`, so there are no dangling feed or product streams: model
  boundaries with the `Source` and `Sink` process steps.
- **No DEXPI 2.0 process/BFD example exists anywhere.** `reference_pid.xml` is a
  P&ID built on the Plant model and is the only published 2.0 instance file.
  `gitlab.com/dexpi/TrainingTestCases` holds only Proteus-era 1.2/1.3 P&IDs.
  `examples/flash_separation_bfd.xml` in this repository is a hand-authored one that
  validates clean.
